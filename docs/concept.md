# コンセプト

## 一言で

> **旅行から帰ってきたら、旅行記が9割できている。**

## 解く課題

旅行の記録は、ほとんどの人にとって「撮った写真がスマホに埋もれたまま」で終わる。

理由は単純で、**記録を残す作業が旅行の後に発生するから**である。旅行中は楽しむのに忙しく、
帰宅後は日常に戻る。「あとで整理しよう」と思った写真は二度と開かれない。

一方で、旅行中のデータは**すでに大量に自動で残っている**。

- スマホは常に GPS 軌跡を記録している
- 写真には撮影時刻と位置が埋め込まれている
- チェックインすれば店名が残る
- 歩数計は歩いた量を記録している

つまり **素材はすでに揃っているのに、束ねる人がいない** というのが本質的な課題である。

本サービスは、この束ねる作業を自動化する。ユーザーがやることは「訂正」と「感想を書き足す」だけにする。

## 何を作るのか

複数のデータソースから自動収集した観測データを、**旅行という単位**で束ね、
**地図と時系列と写真からなる読み物**を生成するサービス。

```
[GPS] [写真] [チェックイン] [歩数] [KML]
   │     │        │          │      │
   └─────┴────────┴──────────┴──────┘
                  ↓ 正規化
            Observation（不変の観測）
                  ↓ 導出
        Stay（滞在） / Move（移動）
                  ↓ 束ね
              Trip（旅行1件）
                  ↓ 生成
         旅行記ページ（地図＋時系列＋写真）
```

## 既存 OSS との差別化

同種の OSS は多数存在するが、**それらとは戦う場所が違う**。

### 既存 OSS の地図

```
        自動収集                      手入力
          │                             │
GPS中心   Dawarich / GeoPulse / Reitti  │
          │                             │
旅行記    ★ 本サービス      ←────→    AdventureLog
```

- **Dawarich / GeoPulse / Reitti** — GPS ログの可視化。主戦場は**日常のライフログ**であり、
  「今年どこを通ったか」を地図上のヒートマップで見るのが主用途。旅行という単位を持たない
- **AdventureLog** — 旅行記だが**完全手入力**。自動収集をしない
- **Timelinize** — 思想は近い（全個人データを1タイムラインに統合）が、粒度が「人生全部」であり、
  旅行という区切りも、読み物としての出力も持たない

### 本サービスが取る立ち位置

**自動収集 × 旅行単位 × 読み物としての出力**、この3つの交差点。

具体的に既存 OSS がやっていないこと:

1. **旅行の自動検出** — 生活圏からの離脱を検出し、「2026/03/14〜17 の京都旅行」を勝手に作る
2. **観測の重ね合わせ** — GPS の点列に写真・チェックイン・歩数・天気を時刻で突き合わせ、
   「14:20 清水寺に45分滞在、写真12枚、この間3,200歩、晴れ18℃」という**1行のイベント**にする
3. **訂正が壊れない設計** — 自動検出は必ず間違える。人手の訂正がアルゴリズム変更後も残る
4. **日本の交通文脈** — 交通系IC の履歴取り込み。既存 OSS は誰もやっていない

## 設計の2本柱

### 1. 観測（Observation）と解釈（Interpretation）の分離

GPS 点も写真もチェックインも、すべて「時刻・位置・ソース・生ペイロード」を持つ
**不変の観測**として貯める。そこから滞在／移動セグメントを導出し、さらに旅行に束ねる。
**この導出結果はいつでも捨てて再計算できる。**

なぜこうするか:

- 検出アルゴリズムは必ず後で変えたくなる。パラメータ調整のたびに生データを失うわけにいかない
- 後から予約メール連携を足したら、**過去の旅行も作り直したい**
- ソースごとに精度と粒度が違う（GPS は密で不正確、チェックインは疎で正確）。
  重ね合わせのルールは実データを見ながら育てるしかない

### 2. 訂正（Correction）が一級市民

自動検出は必ず間違える。以下は日常的に起きる:

- 駅前のホテルに泊まったのに、滞在地点が「駅」と判定される
- 昼食のために立ち寄った店が、短すぎて滞在として検出されない
- 帰宅途中に寄り道したせいで、1つの旅行が2つに割れる

これらの訂正を**生データとも導出結果とも別のレイヤー**に永続化し、
再計算しても消えないようにする。既存 OSS はここが弱い。
**実用に耐えるかどうかはここで決まる。**

## 非目標（やらないこと）

明示的にスコープ外とする。これらは既存ツールが十分に解決している。

- **リアルタイム位置共有** — 家族に現在地を見せる用途。Dawarich や Life360 の領域
- **日常のライフログ全般** — 通勤経路のヒートマップなど。旅行に絞ることで設計を単純に保つ
- **写真そのものの保管・管理** — Immich / PhotoPrism の領域。本サービスは EXIF メタと参照のみ扱う
- **旅行の計画・予約** — 行く前の話。本サービスは行った後を扱う
- **SNS 的な機能** — フォロー、いいね、コメント。読み物を共有できれば十分

## 成功の判定基準

このサービスが成功したかどうかは、以下で判定する。

1. 旅行から帰った直後に開いて、**訂正が10箇所以下**で済むこと
2. 生成された旅行記を、**旅行に行っていない人が読んで内容が分かる**こと
3. 3年前の旅行を開いたときに、**自分が忘れていたことを思い出せる**こと

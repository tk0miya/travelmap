# 機能一覧

MVP・第2段階・第3段階の3層に分ける。

**MVP の制約**: 当初想定の5つのデータソース（GPS / Swarm / 歩数 / KML / 写真）**だけで成立させる**。
第2段階以降のソースに依存しないこと。これが守れていれば、追加ソースが手に入らなくても
サービスとして立つ。

---

## MVP

これが動けば、既に価値がある。

### F-01: 観測の取り込み

| 入力 | 方式 |
|---|---|
| GPS | dawarich 形式の HTTP POST を受信 |
| Swarm チェックイン | Webhook 受信 |
| 写真 | **ディレクトリのスキャン（インデクサ型）**。ローカル / NAS のフォルダをマウントし、JPG / HEIC の EXIF から時刻・位置・向きを抽出。**原本はコピーしない**（D-12） |
| KML | ファイルアップロード |
| 歩数 | Health Connect API から定期取得 |

**受け入れ条件**
- すべての入力が Observation として同一形式で保存される
- `source_record_id` により、同じデータを2回取り込んでも重複しない
- 位置情報を持たない写真も取り込める（時刻だけで後の突き合わせに使う）
- **HEIC の EXIF が JPG と同等に読める**（ISO BMFF ボックス内にあるため JPEG 用パーサでは読めない。
  ネイティブパーサ + exiftool の二段構えとする）
- **EXIF Orientation がサムネイル生成時に焼き込まれる**（原本は書き換えない）
- **Live Photo（HEIC + MOV）とバースト撮影がグルーピングされ、代表1枚が表示される**
- **重複が排除される**。判定キーは「撮影時刻 + カメラ機種 + 元画素数」。
  バイト一致では不十分（Takeout 経由の写真は再エンコードされ原本と一致しない）。
  自動で消さず、候補を提示して人が確定する
- 写真の原本は保存せず、**メタデータとサムネイルのみ自前で持つ**（D-08）
- **写真ディレクトリのスキャンが差分実行できる**（パスと mtime で既知ファイルをスキップ）
- **原本ファイルが移動・削除されても、メタとサムネが残り旅行記が壊れない**
- **Google Takeout の展開ディレクトリが、通常の写真フォルダと同じ経路で処理できる**
- 取り込み失敗時、**どの行が失敗したかが分かる**（全体を巻き戻さない）

**セットアップの受け入れ条件**: 写真取り込みの設定が **volume マウント1つ**で完了すること。
外部プロダクト（Immich 等）の構築を前提条件にしない（D-12）。

**対象外**: Google Photos の継続同期（技術的に不可能。D-09 参照）。

### F-02: タイムゾーン解決と時刻の正規化

**受け入れ条件**
- すべての Observation が UTC で保存される
- 座標から IANA タイムゾーン名を導出し `observed_tz` に記録する
- 座標を持たない観測は、時間的に最も近い座標付き観測の TZ を継承する
- **写真の TZ が以下の優先順で解決される**（EXIF `DateTimeOriginal` は TZ を持たないため）
  1. `OffsetTimeOriginal` があればそれを使う
  2. 写真に GPS 座標があれば座標から導出する
  3. 時間的に最も近い GPS 観測の TZ を借りる
  4. Trip に紐づいた後に Trip の `home_tz` で解決する
- **解決できなかった TZ は NULL ではなく「不明」として明示的に保持され**、後から解決できる
- 解決の出所が `tz_source` に記録される

### F-03: 滞在・移動セグメントの自動検出

GPS 点列を Stay と Move に分解する。

**受け入れ条件**
- Stay と Move が交互に並び、時間的な隙間・重複がない
- 観測が存在しない区間は `is_gap = true` の Move になる（滞在と誤判定しない）
- 各 Segment が `derived_from` で根拠 Observation を辿れる
- 閾値がコード内にハードコードされておらず、設定で変更できる
- **再実行すると同じ入力から同じ結果が出る**（決定的であること）

### F-04: 観測の重ね合わせ

Stay / Move に、他ソースの観測を時刻で突き合わせる。

**受け入れ条件**
- Swarm チェックインが時間的に含まれる Stay に紐づき、`place_source = swarm_checkin` になる
- 写真が撮影時刻に対応する Stay / Move に紐づく
- 歩数が Segment の期間で按分・集計される
- チェックインと写真 EXIF の座標が数百 m ずれていても、両方が保持される
- **位置情報を持たない写真の位置が、撮影時刻から GPS 軌跡を使って逆算される**
- 逆算した位置が `location_source = inferred_from_gps` として記録され、
  EXIF 由来（`exif`）と区別できる。UI 上でも推定であることが示される

### F-05: 旅行の自動検出

**受け入れ条件**
- 自宅（生活圏）から一定距離以上離れ、一定時間以上経過した区間が Trip になる
- 生活圏は過去の滞在頻度から自動推定する（手動設定も可能）
- Trip に属さない日常の Segment も保持される（捨てない）
- 閾値が設定変更可能

### F-06: 旅行ビュー

1つの旅行を1ページで見る。

**構成**
- 地図（軌跡＋滞在ピン。gap 区間は破線）
- 日別のタイムライン（Stay / Move が時系列に並ぶ）
- 各イベントに写真サムネイル、滞在時間、歩数
- サマリ（期間、訪問地数、総移動距離、総歩数）

**受け入れ条件**
- 日の区切りが現地時間 04:00 になっている
- 日付変更線をまたぐ旅行で日数が破綻しない
- 推定に過ぎない情報（`place_source = osm_poi` など）が、確定情報と視覚的に区別される
- 写真が数百枚あってもページが実用的な速度で開く

### F-07: 訂正 UI

**操作**
- 滞在の統合 / 分割
- 場所の付け替え（Place を選び直す）
- 移動手段の変更
- 旅行の境界変更、統合 / 分割
- Segment の除外（誤検出を消す）

**受け入れ条件**
- 訂正が Correction として anchor 方式で保存される
- **セグメントを再計算しても訂正が残る**
- 再適用できなかった訂正が「孤児」として一覧でき、手動で再割り当てできる
- 訂正を取り消せる

### F-08: 注釈の記述

**受け入れ条件**
- 旅行 / 日 / 滞在 / 移動 / 写真それぞれに Markdown で文章を書ける
- 再計算で消えない

## 第2段階

MVP の精度と表現力を上げる。

### F-11: 予約メール取り込み

Gmail API / IMAP からホテル・航空券・レンタカーの確認メールを取得しパースする。

**価値**: 旅行の境界と宿泊地が**確定**する。自動検出の精度が最も大きく上がる。

**受け入れ条件**
- 対応業者のフォーマット一覧が文書化されている
- パース失敗が握りつぶされず、失敗したメールが一覧できる
- 予約情報が Trip の境界検出に優先的に使われる

### F-12: 逆ジオコーディングと Place 名寄せ

Nominatim / Overpass で座標 → POI 名を引き、Place マスタに正規化する。

**受け入れ条件**
- 外部 API の結果がキャッシュされ、同じ座標で繰り返し問い合わせない
- 名寄せ候補が自動提示され、**確定は人が行う**
- 名寄せ後、「この場所に何回行ったか」が数えられる

### F-13: 環境データの後付け

**受け入れ条件**
- Open-Meteo から過去天気（気温・降水・天候）を取得し、Segment に付与
- 標高を取得し、Move の獲得標高を計算
- ユーザーの操作を一切必要としない

### F-14: 旅行記の公開ページ

**受け入れ条件**
- 旅行単位で公開 URL を発行できる
- URL を知っている人だけが読める（推測困難なトークン）
- 公開を後から取り消せる
- 公開ページには自宅座標・生活圏など**旅行と無関係な位置情報が一切含まれない**
- **配信する画像が必ず再生成され、EXIF / XMP / IPTC が全除去されている**（D-10）。
  原本をそのまま配信しない。例外を作らない。
  EXIF には自宅座標・カメラのシリアル番号・本名・元ファイルパスが入りうる
- 公開範囲を「この滞在は隠す」単位で制御できる

### F-15: Immich 連携

Immich の API からアセットのメタデータとサムネイルを取得する。

**価値**: **iPhone の写真を自動収集する唯一の現実的な経路**。iOS の PhotoKit はアプリ内からしか
使えずサーバから叩けないため、自前でやるならモバイルアプリを作るしかない。
Immich は自動バックアップアプリを既に持っているので、そこに乗る。

**受け入れ条件**
- Immich から取得したアセットが、ディレクトリスキャン経路のものと**同一の Asset として扱われる**
  （アダプタ層で正規化され、表示ロジックが分岐しない。D-02 / D-12）
- 原本は取得せず、メタデータとサムネイルのみ保持する（D-08）。
  **サムネイルは Immich の URL を参照するのではなく取得してキャッシュする**
- ディレクトリスキャンと Immich の両方から入った同じ写真が重複排除される
- **Immich が停止していても、既に取り込んだ旅行記は表示できる**
  （Dawarich 等の完全参照モデルはここで写真が消える）

**既知の制約**: Immich の external library を read-only でマウントしている環境では、
Immich 側がメタデータを編集できない。本サービスは読むだけなので影響しないが、
ユーザーの環境把握として文書化する。

### F-16: 移動手段の推定

速度プロファイル＋歩数から `mode` を推定する。

**受け入れ条件**
- 推定根拠が `mode_source` に残る
- 訂正で上書きできる

## 第3段階

差別化を深める。

### F-21: 交通系IC の取り込み

モバイルアプリで FeliCa を読み、乗降駅と時刻を Observation にする。

**受け入れ条件**
- サイバネコード → 駅名の変換テーブルを持つ
- **カード内に直近20件程度しか残らない制約**が UI で説明されている
- 重複取り込みが排除される（同じ利用履歴を何度読んでも増えない）
- 地下鉄区間の gap が IC カード履歴で埋まる

### F-22: フライト情報による欠損補完

**受け入れ条件**
- 予約メールまたは手入力のフライト番号から経路を取得
- `is_gap = true` の Move の `path` が埋まる
- 外部 API が使えないときも、出発地→到着地の直線で補完できる

### F-23: 支出データの取り込み

**受け入れ条件**
- CSV インポートまたは家計簿 API 連携
- 支出が時刻・場所で Segment に紐づく
- 旅行単位の費用が集計される
- 外貨は当日レートで円換算される

### F-24: 文章のドラフト自動生成

Segment 列から旅行記の下書きを生成する。

**受け入れ条件**
- 生成された文章が Annotation として保存され、**人が編集できる**
- 生成物であることが記録される（人が書いたものと区別される）
- 事実（場所名・時刻・距離）がデータと一致している

## 意図的にやらないこと

`docs/concept.md` の非目標を参照。

- リアルタイム位置共有
- 日常のライフログ全般
- 写真そのものの保管（Immich / PhotoPrism に任せる）
- 旅行の計画・予約
- SNS 的機能（フォロー、いいね、コメント）

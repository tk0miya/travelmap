## 3. 食い違いと解決

**すべて TODO.md 側の判断を採用するか、両立させるかで解決する。**
設計文書側を訂正した箇所は、そう明記する。

### ① R\*Tree は Phase 0 では作らない（設計文書を訂正）

**`docs/tech-stack.md` §2① で「R\*Tree に索引を張れる」と書いたが、TODO.md の判断のほうが正しい。**

TODO.md:
> スコープ内のどのエンドポイントも矩形範囲を取らない（`GET /points` は
> `start_at` / `end_at` / `page` / `per_page` / `order` のみ）。**応答すべきクエリのない索引は
> 挿入時間とストレージを無駄に食う。**

そのうえで検討すると、**Phase 1 でも必要になるとは限らない**。

| Phase 1 のクエリ | 空間索引が必要か |
|---|---|
| 写真と GPS の時刻突き合わせ | ❌ 時刻索引で足りる |
| Place の名寄せ（座標が近い Place を探す） | ❌ Place は数百〜数千件。全走査で足りる |
| 生活圏の判定（滞在頻度） | ❌ Stay が対象。件数が小さい |
| Trip 内の地図表示 | ❌ `trip_id` / 時刻で絞る |
| **地図のビューポート検索**（pan / zoom で範囲内の点を取る） | ✅ **これだけが該当** |

**結論: R\*Tree を追加する条件は「地図 UI にビューポート単位の点取得を実装するとき」だけ。**
それ以外では追加しない。`docs/tech-stack.md` を訂正済み。

### ② 「日」の概念は2つあり、統一してはいけない

これは**見た目が重複しているので、後から誰かが統一して壊す**類の箇所。

| | 切り方 | 用途 | 変えられるか |
|---|---|---|---|
| **`daily_stats.day`** | `TRAVELMAP_TIMEZONE`（サーバ設定・単一）の **0:00** | Dawarich 互換の `/stats` と `tracked_months` | **変えられない。** アプリの表示と一致させる必要がある |
| **Trip の「N 日目」** | その時点の**現地時間の 04:00**（D-07） | 旅行記の日別タイムライン | Phase 1 の裁量 |

**なぜ分けるのか**

- `daily_stats` は**アプリに見せる数字**。アプリ側の集計と一致しないとバグに見える。
  TODO.md も「日本で `Asia/Tokyo` を設定せずに動かすと 00:00〜09:00 の移動が前日に付き、
  `/stats` と `tracked_months` がアプリと食い違う」と指摘している
- Trip の日は**人が読む単位**。23:00 にホテルへ戻って翌 01:00 まで起きていたなら同じ「1日」。
  0:00 で切ると深夜移動が日をまたいでしまう（D-07）

**両方必要であり、片方に寄せると必ずどちらかが壊れる。**

### ③ points はソフトデリートにする（Phase 0 で仕込む）

**これは Phase 0 の時点で入れておかないと後から復元できない。**

- 設計文書 D-05: **Observation は不変・追記のみ**
- TODO.md: `PATCH /api/v1/points/{id}`（緯度経度を編集）、`DELETE /api/v1/points/{id}`、
  `DELETE /api/v1/points/bulk_destroy`

Dawarich 互換のためには点の編集・削除に応じる必要があり、素朴に実装すると物理削除になる。
しかし**アプリからの削除は意味的には「訂正」である**（ユーザーが「この点は誤りだ」と言っている）。
物理削除するとその事実が失われる。

**解決: `points` に `deleted_at` を持たせ、物理削除しない。**

得られるもの:

1. Dawarich API は `deleted_at IS NULL` で絞って返す。**互換性に影響しない**
2. Phase 1 の解釈層が「ユーザーが消した点」を知れる。D-06 の Correction と接続できる
3. 再計算が安定する。物理削除だと再計算のたびに結果が変わりうる

**コストは1カラムと `WHERE` 句1つ。** 後から入れると、それまでに消された点の情報は戻らない。

同様に、編集された点には `edited_at` を持たせ、**元の値を別に残す**ことを推奨する
（`original_lat` / `original_lon`、または監査テーブル）。
D-05 の「生データは失わない」を Dawarich 互換と両立させる最小の方法である。

### ④ 写真対応時にベースイメージが変わる

- TODO.md Distribution: `CGO_ENABLED=0` → `gcr.io/distroless/static`（バイナリ＋CA バンドルのみ）
- `docs/tech-stack.md` §3: libvips / exiftool を外部プロセスとして呼ぶ

**Phase 0 は写真を扱わないので `distroless/static` で正しい。**
しかし Phase 1 で写真を扱うと、**イメージに libvips と exiftool が入るため `distroless/static` を
維持できない**。debian-slim ベース＋150〜200MB になる（`docs/tech-stack.md` §3 の見込みと一致）。

**Go バイナリ自体は `CGO_ENABLED=0` のままでよい**（外部プロセス方式を選んだ理由がここにある）。
変わるのはベースイメージだけ。

Phase 0 の `Dockerfile` を書くとき、**この変更が来ることを前提に multi-stage の構成を決める**こと。

### ⑤ Dawarich の `tracks` は Segment の `Move` ではない

**これは混同すると「tracks を実装したから Move は済み」と誤解する箇所。**

| | 定義 | 含むもの |
|---|---|---|
| **Dawarich の `track`** | **記録が途切れていない区間**（`TRAVELMAP_TRACK_BREAK_MINUTES` 以上の空白で分割） | 滞在も移動も**両方**含む |
| **設計文書の `Move`** | **滞在と滞在の間の移動** | 移動のみ |

`track` は「記録セッション」、`Move` は「滞在間の移動」。**粒度も意味も違う。**

一方 **Dawarich の `visits` は設計文書の `Stay` とほぼ同じ**（滞在検出の結果）。
ここは検出ロジックを共有でき、テーブルを二重に持つ必要はない。

**したがって Phase 0 Milestone F は F-03 を部分的にしか満たさない。**
Step 14（Visits = 滞在検出）は F-03 の滞在側に相当するが、
Step 13（Tracks）は F-03 の移動側ではない。Phase 1 で `Move` を別に導出する必要がある。

## 4. TODO.md から得られた新しい知見

設計文書側に取り込むべき事実。

### Dawarich には「404 = 未対応」という機能検出プロトコルがある

TODO.md より:
> Dawarich にはバージョンネゴシエーションがない。機能検出はエンドポイントを呼んで
> **404 を「このサーバはこの機能を持たない」と解釈し、クライアントは機能を完全に隠す**
> ことで行われる。

**未実装のエンドポイントで空配列や空オブジェクトを 200 で返してはならない。**
200 は「機能が存在する」と伝えることになり、アプリが壊れた UI を出す。

これは設計上ありがたい性質で、**実装しないことが「持っていない」と伝える正式な手段になる**。

### `GET /api/v1/points` は HEAD に応答しなければならない

クライアントは同じクエリで `HEAD` を投げ、`X-Total-Pages` を読んでからページを取る。
**このヘッダが無い、または 0 だと、クライアントは「取るものがない」と判断して止まる**（地図が空になる）。

chi はメソッドを明示登録するため、`r.Get` だけでは HEAD に 405 を返す。

### iOS アプリはクローズドソース

`dawarich-app/dawarich-ios` は空リポジトリ。実際に呼ばれるエンドポイント・必須フィールド・
呼び出し順は仕様書からは判らない。

補う手段は2つ。**コミュニティ製の Android クライアント（`sunstep/dawarich-community`）の
HTTP 層を読むこと**と、**実機に対するリクエストログ**（Step 6）。
上記の HEAD 要件と「全エンドポイントで Bearer を受けるべき」はいずれも前者から判明した。

### ソーシャルログインが必須だと Milestone B が完了しない可能性がある

`POST /api/v1/auth/apple` / `auth/google` が仕様に存在する。
iOS アプリが Sign in with Apple を強制する場合、`auth/login` だけでは接続成功に至らない。
**Step 5 で最初に確認すべきリスク。**

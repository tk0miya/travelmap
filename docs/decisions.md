# 決定事項

設計上の重要な選択と、その理由を記録する。

> **注記**: D-01 〜 D-04 は**暫定決定**である。設計を前に進めるために推奨案を置いたもので、
> 確認が取れ次第このファイルを更新する。それぞれ「覆したときの影響」を明記してあるので、
> 変更コストを見てから判断できる。

---

## D-01: サービスの軸は「旅行記の自動生成」（暫定）

### 決定

日常も含むライフログではなく、**旅行という単位に絞る**。出力は統計ダッシュボードでも
生ログビューアでもなく、**人に見せられる読み物**とする。

### 理由

GPS ログ可視化のレイヤーは飽和している（`docs/research.md` 参照）。Dawarich が 9,000★ を集め、
GeoPulse と Reitti が後を追い、いずれも滞在・移動検出と Immich 連携を実装済み。
ここに同じものを作っても既存 OSS の劣化版にしかならない。

一方、**自動収集された素材から旅行記を生成する**領域は空いている。
AdventureLog は旅行記だが完全手入力、Timelinize は統合するが旅行の概念を持たない。

旅行に絞ることには設計上の利点もある。日常を含めると「生活圏の移動」という
情報量の低いデータが大半を占め、検出も表示も難しくなる。旅行だけなら
**イベント密度が高く、境界が明確**で、設計がずっと単純になる。

### 覆したときの影響

**小さい**。日常も対象にする場合、Trip に属さない Segment を捨てない設計に既になっているため、
データモデルの変更は不要。表示側に「日常ビュー」を足すだけで済む。

## D-02: 既存 OSS とは「両対応のアダプタ層」で付き合う（暫定）

### 決定

観測の取り込みを**抽象化されたアダプタ層**にし、以下の両方を受けられるようにする。

- dawarich 形式の push を**直接受信**して自前 DB に保存する
- Immich など外部サーバの API から**取得**する

### 理由

「Dawarich を必ず立てる」前提にすると、GPS のためだけに Rails アプリを運用させることになり、
セルフホストのハードルが上がる。一方「全部自前」にすると、写真管理まで作ることになって
スコープが破綻する。

分岐点は**そのデータの主たる置き場所がどこか**である。

- **GPS 軌跡** — 本サービスが主たる置き場所であるべき。旅行記の骨格そのものであり、
  外部依存にすると外部が落ちたときに何も表示できない。よって**直接受信して自前保管**
- **写真** — 本サービスが主たる置き場所であるべきではない。数十 GB の
  バイナリ管理は Immich の仕事。よって**EXIF メタと参照だけ持つ**

この使い分けをアダプタ層で吸収する。

### 覆したときの影響

**中程度**。アダプタ層を最初から入れておけば、後から「やはり Dawarich API 経由にする」も
「やはり写真も自前保管する」も、アダプタの追加で済む。逆に**アダプタ層を入れずに始めると
覆すのが高くつく**ため、ここは最初から入れる価値がある。

## D-03: 公開範囲は「自分用＋旅行記だけ公開リンク」（暫定）

### 決定

- 収集・編集は**シングルユーザー前提**。認証は最小限
- 完成した旅行記に限り、**推測困難なトークン付き URL** で公開できる
- 公開ページには旅行と無関係な位置情報を一切含めない

### 理由

位置情報は最も機微な個人データの一つである。自宅の座標、生活圏、行動パターンが
漏れると実害が出る。一方で「旅行記を人に見せたい」という欲求は自然で、
それが無ければ読み物として作る意味が薄い。

この2つを両立させる最小の構成が「収集は完全プライベート、成果物だけ選択的に公開」である。

マルチユーザー化を最初から入れないのは、**認証・認可・テナント分離が
設計時間の大半を食う**ため。シングルユーザーで価値を確かめてからでよい。

### 覆したときの影響

**大きい**。後からマルチユーザー化するには、全テーブルに所有者を足し、
全クエリにスコープを入れる必要がある。ただし**旅行記の公開機能を先に作っておけば
その基盤（トークン、公開範囲制御）は流用できる**ため、完全な作り直しにはならない。

一般公開 SaaS にする場合は、運用・法務・スケールの検討が別途必要であり、
これは本設計のスコープ外。

## D-04: 初期スコープのデータソースは当初の5つ（暫定）

### 決定

MVP は **GPS / Swarm / 歩数 / KML / 写真** の5つだけで成立させる。
予約メール・IC カード等は第2段階以降。

### 理由

追加ソース（特に予約メール）は自動検出の精度を大きく上げるが、
**パーサの保守コストが継続的にかかる**。業者ごとにメールのフォーマットが違い、
向こうの都合で変わる。MVP でこれを抱えると、本質でないところで手が止まる。

まず5つで「旅行記が9割できている」状態を作り、**どこが足りないかを実データで確かめてから**
追加ソースを選ぶ。先に想像で決めると、効かないものを作り込むことになる。

### 覆したときの影響

**小さい**。Observation が汎用形式なので、ソース追加はアダプタ1つの追加で済む。
これがこのデータモデルを選んだ理由でもある。

## D-05: 解釈層は再計算可能、訂正層は永続

### 決定

Segment / Trip は**いつでも全削除して再構築できる**。
Observation と Correction / Annotation だけが失ってはならないデータ。

### 理由

検出アルゴリズムは必ず後で変わる。閾値の調整、新しいソースの追加、
バグの修正 — そのたびに過去のデータを作り直したくなる。

再計算不可の設計にすると、**アルゴリズムを改善するたびに過去の旅行が古いまま取り残される**。
これは長く使うほど効いてくる負債になる。

### 覆したときの影響

**極めて大きい**。この原則を崩すと、以降すべての設計判断が変わる。覆さない前提で進める。

---

## D-06: 訂正は Segment ID ではなく anchor に紐づける

### 決定

Correction / Annotation は Segment の ID ではなく、**時刻範囲＋座標範囲（anchor）** を持つ。
再計算後は anchor で照合して再適用する。

### 理由

D-05 により Segment は再計算のたびに ID が変わる。ID に紐づけた訂正は再計算で全て無意味になる。
一方、**時刻と場所は再計算しても大きくは変わらない**ため、これを鍵にすれば追随できる。

再適用できなかった訂正は「孤児」として保持し、UI で提示する。
アルゴリズム変更で訂正が浮くことは必ず起きるので、黙って捨てるのは許容できない。

### 覆したときの影響

**大きい**。ただし D-05 を前提にすると他に選択肢がない。

## D-07: 時刻はすべて UTC 保存、TZ を併記

### 決定

すべての Observation を UTC で保存し、座標から導出した IANA タイムゾーン名を併記する。
日の区切りは**現地時間 04:00** とする。

### 理由

海外旅行のタイムライン破綻の最大要因がタイムゾーンである。
デバイスのローカル時刻で保存すると、日付変更線をまたいだ瞬間に時系列が壊れる。

日の区切りを 00:00 ではなく 04:00 にするのは、**深夜移動が「日をまたいだ」ことにならず
体感と一致する**ため。23:00 にホテルに戻って翌 01:00 まで起きていた場合、
それは同じ「1日」として扱われるべき。

### 覆したときの影響

**極めて大きい**。時刻の扱いは後付けが最も困難な部分。最初から入れる。

## D-08: 写真はメタデータとサムネイルだけ自前で持ち、原本は参照にとどめる

### 決定

写真を3層に分ける。

- **メタデータ** — 必ず自前で持つ
- **サムネイル** — 自前で持つ
- **原本バイナリ** — 持たない。外部への参照のみ

### 理由

**原本へのリンクが切れても旅行記が壊れないようにするため。**

原本は重く、所有権が曖昧である（Immich にある / NAS にある / iPhone にしかない）。
写真管理サーバの乗り換えや NAS の入れ替えは起きる。そのたびに旅行記が壊れるのは許容できない。

一方、メタとサムネは軽く自前で抱えられる。**この2つだけあれば旅行記は何年でも生き残る。**
原本が引けなくなっても、失われるのは拡大表示だけ。

逆に原本を自前で抱えると、ストレージ管理・バックアップ・重複排除・トランスコードという
写真管理サービスの仕事が全部降ってくる。これは `docs/concept.md` の非目標に反する。

### 覆したときの影響

**小さい**。`Asset.original_ref` を「参照」から「自前保管」に変えるのは追加であって変更ではない。
逆方向（自前保管から参照へ）は移行が必要になるため、参照から始めるのが安全側。

詳細は `docs/photos.md`。

## D-09: Google Photos は継続同期のソースにしない

### 決定

Google Photos を定期同期のデータソースとして設計に入れない。
Google Takeout によるワンショット取り込みのみ、過去分の移行経路として扱う。

写真の主たる流入経路は **ディレクトリのスキャン（MVP、D-12）** と **Immich 連携（第2段階）** とする。
Takeout の展開ディレクトリは前者と同じ経路で処理する。

### 理由

**技術的に不可能である。** 2025/3/31 に Library API から
`photoslibrary.readonly` / `.sharing` / `photoslibrary` のスコープが削除され、
残る `photoslibrary.readonly.appcreateddata` では自アプリがアップロードしたものしか読めない。

代替の Picker API は存在するが、「ユーザーが都度ピッカーで選ぶ」前提の設計であり、
**旅行1回あたり数百枚を毎回手で選ばせる運用は成立しない**。

なお Immich を第2段階に置くのは、単なる利便性ではない。
**iOS の PhotoKit はアプリ内からしか使えずサーバから叩けない**ため、
iPhone の写真を自動収集するには自前モバイルアプリを作るしかない。
Immich は自動バックアップアプリを既に持っているので、そこに乗るのが唯一現実的な経路になる。

### 覆したときの影響

**覆せない**（Google 側の制約であり、こちらの判断で変えられない）。
将来 Google が方針を戻した場合は、アダプタを1つ足すだけで済む（D-02 のアダプタ層の利点）。

## D-10: 公開ページの画像は必ず再生成し、メタデータを全除去する

### 決定

旅行記の公開ページで配信する画像は、**原本をそのまま配信しない**。
必ず再生成し、EXIF / XMP / IPTC を全て落とす。例外を作らない。

### 理由

D-03 で「公開ページに旅行と無関係な位置情報を含めない」と決めたが、
**EXIF 経由の漏洩を明示していなかった**。EXIF には以下が入りうる。

- 自宅で撮った写真の GPS 座標
- カメラのシリアル番号（個体の追跡が可能になる）
- 撮影者名・著作権表記に入れた本名
- 元のファイルパス（ユーザー名が含まれることがある）

表示上は旅行の写真に見えても、メタデータには旅行と無関係な情報が残る。
「表示している内容」と「配信しているバイト列」は別物であり、後者を管理しないと意味がない。

**例外を作らないのが重要。** 「この写真は大丈夫」という判断をユーザーに委ねると必ず漏れる。

### 覆したときの影響

覆さない。セキュリティ上の下限として扱う。

## D-11: 所有するのは原本ではなく「紐付け」

### 決定

本サービスは**オーケストレーター（全て外部依存）でも、自己完結型（全て自前保管）でもない**。

- **生データの原本は所有しない** — 写真バイナリは NAS でも Immich でもよい
- **解釈（紐付け）は絶対に所有する** — どの写真がどの旅行のどの滞在に属するか、
  場所の判定は推定か確定か、ユーザーが何をどう訂正したか

### 理由

「コンダクター／オーケストレーターに徹するか、すべて自分で管理するか」という問いに対する答え。
**どちらの極も個人開発では破綻する。**

**完全オーケストレーターの問題**: サービスの価値が**連携先の数に比例する**。
連携先を増やすほど価値は上がるが、保守コストも比例して上がる。
各サービスの API 変更に永続的に追随し続ける必要があり、個人開発では持たない。

**完全自己管理の問題**: 写真管理という**別レイヤーの仕事を丸ごと抱える**。
ストレージ、バックアップ、トランスコード、重複排除。本質でないところで手が止まる。

**第3の道**: 生データの所有は譲るが、解釈の所有は絶対に譲らない。

この立場の実利は、**連携先が消えても価値が消えないこと**である。
Immich をやめても、NAS を入れ替えても、Google Photos が閉鎖されても、
「2026年3月の京都旅行の3日目、清水寺に45分いた」という情報は手元に残る。
失われるのは写真の拡大表示だけ。

これは D-05（解釈層は再計算可能、訂正層は永続）および D-08（3層分離）と一貫している。
**外部に置けるのは「重くて代替可能なもの」だけ**、というのが共通の判断基準。

### 覆したときの影響

覆さない。これは D-05 / D-08 から導かれる帰結であり、本サービスの立ち位置そのもの。

## D-12: 写真の取り込みはインデクサ型を MVP とする

### 決定

MVP はローカル / NAS のディレクトリをスキャンする**インデクサ型**とする。
**原本はその場に置いたままコピーしない。** Immich 連携は第2段階。

### 理由

「外部サービス API 連携」と「ローカルファイル読み取り」の2択に見えるが、
**両者の間に「ローカルを読むが原本は持たない」インデクサ型がある**。
Immich 自身が external library としてこの方式を持っており、需要が実在する証拠になる。

**セットアップしやすさは直感と逆になる。**

| 方式 | 第三者のセットアップ手順 |
|---|---|
| オーケストレーター型 | 「まず Immich を立ててください」＝ 別プロダクトの構築が前提条件に入る |
| インデクサ型 | 「写真フォルダをマウントしてください」＝ `volumes:` を1行 |

外部連携のほうが利用しやすいという見立ては誤りで、**前提条件に別プロダクトの構築が入る時点で
脱落要因になる**。

加えて、インデクサ型は **Google Takeout の展開ディレクトリも同じ経路で処理できる**ため、
取り込み経路を増やさずに Google Photos 利用者を拾える。

Immich 連携を第2段階に残すのは、**iOS の PhotoKit がサーバから叩けない**ため。
iPhone の写真を自動収集するには自前モバイルアプリが要り、MVP のスコープを超える。
Immich は自動バックアップアプリを持っているので、そこに乗るのが唯一現実的な経路になる。

### 連携先に Immich を選ぶ理由（他の画像管理サービスとの比較）

API を提供する画像管理サービスは Immich だけではない。PhotoPrism / LibrePhotos /
Nextcloud Memories / Piwigo / Lychee / Ente、Synology Photos、Flickr などを比較した（`docs/photos.md` §5）。

**評価軸5つのうち、差がつくのは1つだけだった。**

| 軸 | 結果 |
|---|---|
| GPS 付き EXIF が取れるか | どれも取れる。差がつかない |
| サムネイルが取れるか | どれも取れる。差がつかない |
| 運用コスト | **PhotoPrism・Piwigo のほうが Immich より軽い** |
| API の安定性・文書化 | **PhotoPrism のほうが Immich より優れている** |
| **スマホからの自動バックアップ** | **Immich だけ** |

**運用コストと API 安定性では Immich が負けている。** PhotoPrism は 4GB の Raspberry Pi で動き、
API は Swagger で文書化され、RAW も 30 形式以上に対応し、Dawarich が既に連携対応済みである。

それでも Immich を選ぶ理由は**スマホからの自動バックアップ経路が他に存在しない**という一点に尽きる。
「既存 OSS が Immich を使っているから」ではない。

裏返すと、**スマホ写真の自動取り込みを求めないなら、画像管理サービスを挟む意味自体が薄い**。
PhotoPrism を挟んでも得られるのは「EXIF パース済み・サムネイル生成済み」だけで、
それは libvips + exiftool で数百行に収まる。この場合はインデクサ型のほうが軽くて確実。

なお **Ente は E2EE のため設計上除外**（原本が暗号化され API から読めない）、
**Flickr は IPTC / XMP をデフォルトで剥がすため不適**（メタデータこそが欲しいもの）、
**Synology Photos は API が完全に非公式・無文書で DSM 更新により壊れうる**。

### 汎用化コストについて

「経路を増やすと汎用化コストがかかる」という懸念は、コストの発生場所を取り違えている。
高いのは経路の数ではなく、**内部表現がソースごとに違うこと**。

アダプタ層で Asset に正規化すれば、経路追加は各 50〜150 行程度で済む。
**アダプタ層を作るコストは1回、作らないコストは永続。** D-02 の決定がそのまま効く。

### 覆したときの影響

**小さい**。D-02 のアダプタ層があるため、MVP をインデクサ型にするか Immich 連携にするかは
アダプタの実装順の問題でしかない。順序の入れ替えで対応できる。

## 未決定（実データを見ないと決められない）

以下は実装フェーズで実データを使って決める。想像で決めない。

- 滞在判定の閾値（何分・何メートル以内に留まったら滞在か）
- 旅行判定の閾値（自宅から何 km 離れて何時間経過したら旅行か）
- Correction の anchor 照合ロジック（重なり率の閾値）
- Place 名寄せの候補提示ロジック
- 技術スタック（言語・DB・地図ライブラリ）— **次フェーズで検討する**

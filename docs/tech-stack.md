# 技術スタック

**制約: NAS の限られたリソース内で動作させる。**

---

## 1. リソース予算

NAS 8GB で Immich を同居させる場合の想定。

```
NAS 8GB
├─ DSM / OS + 既存サービス        1〜2GB
├─ Immich（4コンテナ、アイドル）   2〜3GB
└─ 残り                          3〜4GB  ← 本サービスの枠
```

**本サービスの目標: 常時 300MB 以下。**

### 参考: 既存 OSS の実測

| | 構成 | メモリ |
|---|---|---|
| **Dawarich** | Rails + PostgreSQL/PostGIS + Sidekiq + Redis | **最低 2GB。1GB では OOM**。大量インポート時に Sidekiq がメモリを食い尽くし Raspberry Pi が応答不能になる [issue #1839](https://github.com/Freika/dawarich/issues/1839)。最近 ~150MiB(20%) 削減の PR あり |
| **GeoPulse** | Java (Quarkus) + Vue | 100MB 未満を標榜 |
| **Timelinize** | **Go + SQLite** | 記載なし。単一バイナリ |

**Dawarich が重いのは Ruby だからではなく、4プロセス構成だから。**
GeoPulse は Java でありながら軽量を標榜している。**言語より構成が効く。**

## 2. 言語より効く3つの判断

**メモリの行き先は言語ではない。** 3〜4GB の枠に対し、言語のベースライン差は 10MB 対 200MB
（全体の 5% 程度）。以下のほうが桁で効く。

### ① DB は SQLite にする（差: 300〜500MB）

Postgres + PostGIS は別プロセスで 200〜500MB を消費する。

**しかし本サービスに必要な地理計算は Haversine 距離程度**であり、PostGIS のフル機能は要らない。
単一ユーザーのセルフホスト（D-03）なら SQLite で十分。

**副次的な利点**: バックアップがファイルコピー1回で済む。NAS 運用と相性が良い。

#### 訂正: R\*Tree は作らない

以前ここに「SQLite の R\*Tree で座標に索引を張れる」と書いたが、**索引は作らない**。
`TODO.md` の判断のほうが正しい。**応答すべきクエリのない索引は挿入時間とストレージを無駄に食う。**

必要になる条件を洗い出すと、該当するのは1つだけだった。

| クエリ | 空間索引 |
|---|---|
| 写真と GPS の時刻突き合わせ | ❌ 時刻索引で足りる |
| Place の名寄せ | ❌ 数百〜数千件。全走査で足りる |
| 生活圏の判定 | ❌ Stay が対象。件数が小さい |
| Trip 内の地図表示 | ❌ `trip_id` / 時刻で絞る |
| **地図のビューポート検索**（pan / zoom で範囲内の点を取る） | ✅ **これだけ** |

**追加する条件: 地図 UI にビューポート単位の点取得を実装するとき。** それまでは作らない。
索引は後から `CREATE` できるので、先に作る理由がない。詳細は `docs/roadmap.md` §3 ①。

### ② プロセスを1つに畳む（差: 200〜400MB）

Dawarich は Rails + Sidekiq + Redis + Postgres の4プロセス。
Web とバックグラウンドジョブを1プロセスに畳めれば数百 MB 浮く。

**これが言語選択と絡む唯一の重要なポイント。** §3 参照。

### ③ スキャンをストリーミングにする（差: 実装次第）

5万枚を一度にメモリへ載せれば**どの言語でも死ぬ**。
Dawarich の Sidekiq OOM はこの類の問題。

**これは言語ではなく実装の問題。** ディレクトリスキャン・EXIF 抽出・サムネイル生成は
すべてストリーミング（1件ずつ処理して即座に解放）で書く。

### 画像処理は言語非依存

**最も重い処理であるデコードとサムネイル生成は libvips / exiftool というネイティブライブラリが行う。**
どの言語から呼んでも実行時間とメモリはほぼ変わらない。**一番重いところが言語に依存しない。**

## 3. 言語比較

| | ベースライン RSS | 単一バイナリ | 1プロセスで HTTP＋バックグラウンド | 画像処理 | ARM64 |
|---|---|---|---|---|---|
| **Go** | **10〜30MB** | ✅ 静的リンク | ✅ goroutine で自然 | govips / exiftool 呼び出し | ✅ `GOOS/GOARCH` だけ |
| **Rust** | 5〜20MB | ✅ | ✅ | libvips バインディング | ✅（ビルドが長い） |
| **TypeScript / Node** | 40〜80MB | ❌ | ✅ worker_threads | **sharp が優秀**（libvips） | ✅ |
| **Python** | 30〜50MB＋依存 | ❌ | △ 工夫が要る | pyvips / pillow-heif | △ wheel 事情に注意 |
| **JVM (Kotlin/Quarkus)** | 100〜300MB | native-image なら可 | ✅ | 選択肢が少ない | ✅ |
| **Ruby / Rails** | 200MB〜 | ❌ | ❌ Sidekiq が別プロセス前提 | 各種 | ✅ |

### 決定: Go（D-13）

1. **Timelinize が Go + SQLite でこのワークロードを実装済み。**
   写真＋位置＋タイムライン統合という、ほぼ同じ問題領域での直接の前例
2. **1プロセスで HTTP とバックグラウンドスキャンが同居できる。**
   goroutine と channel だけで済み、Redis も Celery も不要。②の差がタダで手に入る
3. **言語ランタイムを同梱しなくてよい。** 単一バイナリで配布でき、イメージが小さく保てる
4. **クロスコンパイルが `GOOS/GOARCH` だけ。** NAS の CPU アーキテクチャに悩まされない

#### 注意: 「完全な静的バイナリ」にはならない

libvips を使う以上、**イメージには libvips が入る**。したがって `FROM scratch` にはできず、
debian-slim 等をベースに libvips を入れた構成になる。選択肢は3つ:

| 方式 | cgo | イメージ | 備考 |
|---|---|---|---|
| **govips（cgo バインディング）** | 必要 | libvips 入りベース | 最速。ただし cgo でクロスコンパイルが面倒になる |
| **`vipsthumbnail` / `exiftool` を外部プロセスとして呼ぶ** | 不要 | libvips + exiftool 入りベース | **Go バイナリ自体は静的のままでクロスコンパイルが容易**。プロセス起動コストは1枚あたり数 ms |
| **純 Go の画像処理** | 不要 | 小さい | HEIC 対応が弱く、メモリ効率も libvips に劣る。**不採用** |

**外部プロセス方式を推奨。** クロスコンパイルの容易さという Go の利点を保てるうえ、
`docs/photos.md` §6 ④ で決めた「読めないものだけ exiftool に回す二段構え」とも自然に噛み合う。
SQLite も同様に、cgo 不要の実装（`modernc.org/sqlite`）を選べば静的リンクを保てる。

イメージサイズは数十 MB ではなく **150〜200MB 程度**が現実的な見込み（§4 の目標値と整合）。

#### Phase 0 と Phase 1 でベースイメージが変わる

`TODO.md` の Phase 0 は**写真を扱わない**ため、`CGO_ENABLED=0` のバイナリだけで完結し、
`gcr.io/distroless/static`（バイナリ＋CA バンドルのみ）に置ける。これは正しい。

**Phase 1 で写真を扱うと、イメージに libvips と exiftool が入るため `distroless/static` を
維持できない。** debian-slim ベースの 150〜200MB になる。

**Go バイナリ自体は `CGO_ENABLED=0` のまま**でよい（外部プロセス方式を選んだ理由がここにある）。
変わるのはベースイメージだけ。**Phase 0 の `Dockerfile` を書く時点でこの変更が来ることを
前提に multi-stage の構成を決めること。**

### Python も成立する（条件付き）

**「最も速く書ける言語」はソロ開発では実行効率より重要。** 以下を守れば 150〜250MB に収まる。

- FastAPI + uvicorn を **1ワーカー**で動かす
- **Celery / Redis を使わない。** APScheduler か DB バックドのジョブテーブル＋スレッド
- SQLite を使う（①）
- スキャンはジェネレータでストリーミング（③）

**積極的な理由**: 滞在検出は本質的にクラスタリング問題であり、**試行錯誤が最も多くなる部分**。
ここは numpy が効く。

**注意**: scikit-learn を入れると numpy + scipy で 200MB 超＋ARM wheel の問題が出る。
滞在検出は Li らの逐次スキャン型アルゴリズムなら **100 行程度で sklearn 不要**。
依存を足さずに済ませるべき。

### 避けるもの

| | 理由 |
|---|---|
| **Rails** | Dawarich が最低 2GB を要求している実例がある |
| **JVM** | native-image のチューニングが必要になり、本質でないところで時間を使う |
| **Rust** | MVP では開発速度のコストが見合わない。**滞在検出の閾値など未確定な部分が多い段階では特に**。性能が問題になってから一部を置き換えれば十分 |

## 4. 言語非依存で決まっていること

言語（D-13: Go）とは独立に決まる構成。

| 項目 | 決定 | 理由 |
|---|---|---|
| **DB** | **SQLite**（空間索引なし） | §2 ①。Postgres/PostGIS は過剰。R\*Tree も作らない |
| **プロセス構成** | **1プロセス**（Web＋バックグラウンド同居） | §2 ②。ブローカーを持たない |
| **ジョブキュー** | **DB バックド**（Redis を使わない） | プロセスを増やさない |
| **画像処理** | **libvips**（＋読めないものだけ exiftool） | §2。PhotoPrism の二段構えに倣う（`docs/photos.md` §6 ④） |
| **配布形態** | **Docker イメージ**（単一コンテナ） | NAS の標準的な導入手段 |
| **対応アーキテクチャ** | **amd64 / arm64 の両方** | NAS は両方ありうる |

### 目標値

| 指標 | 目標 |
|---|---|
| 常時メモリ | **300MB 以下** |
| スキャン中のピークメモリ | **500MB 以下**（枚数に比例して増えないこと） |
| Docker イメージサイズ | 200MB 以下 |
| 追加で必要な常駐プロセス | **0**（DB もブローカーも持たない） |

## 5. MVP の依存プロファイル

GPS はモバイルクライアントからの push を受信し（D-02）、写真はローカル / NAS の
ディレクトリをスキャンする（D-12）。したがって:

**MVP が依存する外部サーバは 0。** Dawarich も Immich も Postgres も Redis も起動しない。
本サービスのコンテナ1つと、写真フォルダのマウントだけで動く。

Immich 連携（F-15）は第2段階の**任意**の追加であり、必須にはしない（D-12）。

## 6. Phase 0 で確定した具体スタック

`TODO.md` の「Technical Decisions」「Libraries」で確定した内容。ここでは要点のみ。

| 項目 | 選択 |
|---|---|
| Go バージョン | `go 1.26`（下限は 1.25。`modernc.org/sqlite` v1.56.0 の要求） |
| SQLite ドライバ | `modernc.org/sqlite`（純 Go・CGO 不要）。ベンチマーク後に採択 |
| ルータ | `github.com/go-chi/chi/v5`（**依存ゼロ**。Web UI 追加時に `/api/v1` と `/*` で認証方式を分けるため） |
| ストア | リポジトリインターフェース越し（将来 PostgreSQL 実装を足せる余地） |
| バックグラウンド処理 | goroutine ＋ SQLite のジョブテーブル |
| 開発ツール | `go.mod` の `tool` ディレクティブで golangci-lint / govulncheck / gofumpt を宣言 |

`tool` ディレクティブを使う理由は利便性だけではない。**`golangci-lint` は `go` ディレクティブが
自身のビルドに使われた Go より新しいモジュールの解析を拒否する**ため、事前インストールした
バイナリは `go` ディレクティブの上限を決めてしまう。`go tool` はモジュール自身のツールチェーンで
リンタを再ビルドするので、この天井が構造的に消える。

詳細と実測値は `TODO.md` の「Development Environment」を参照。

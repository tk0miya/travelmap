# 技術スタック

**制約: NAS の限られたリソース内で動作させる。**

---

## 1. リソース予算

NAS 8GB で Immich を同居させる場合の想定。

```
NAS 8GB
├─ DSM / OS + 既存サービス        1〜2GB
├─ Immich（4コンテナ、アイドル）   2〜3GB
└─ 残り                          3〜4GB  ← 本サービスの枠
```

**本サービスの目標: 常時 300MB 以下。**

### 参考: 既存 OSS の実測

| | 構成 | メモリ |
|---|---|---|
| **Dawarich** | Rails + PostgreSQL/PostGIS + Sidekiq + Redis | **最低 2GB。1GB では OOM**。大量インポート時に Sidekiq がメモリを食い尽くし Raspberry Pi が応答不能になる [issue #1839](https://github.com/Freika/dawarich/issues/1839)。最近 ~150MiB(20%) 削減の PR あり |
| **GeoPulse** | Java (Quarkus) + Vue | 100MB 未満を標榜 |
| **Timelinize** | **Go + SQLite** | 記載なし。単一バイナリ |

**Dawarich が重いのは Ruby だからではなく、4プロセス構成だから。**
GeoPulse は Java でありながら軽量を標榜している。**言語より構成が効く。**

## 2. 言語より効く3つの判断

**メモリの行き先は言語ではない。** 3〜4GB の枠に対し、言語のベースライン差は 10MB 対 200MB
（全体の 5% 程度）。以下のほうが桁で効く。

### ① DB は SQLite にする（差: 300〜500MB）

Postgres + PostGIS は別プロセスで 200〜500MB を消費する。

**しかし本サービスに必要な地理計算は Haversine 距離と矩形範囲検索程度**であり、
PostGIS のフル機能は要らない。そして **SQLite には R\*Tree モジュールが標準搭載**されているため、
「この座標の近くの写真」に索引を張れる。

単一ユーザーのセルフホスト（D-03）なら SQLite で十分。

**副次的な利点**: バックアップがファイルコピー1回で済む。NAS 運用と相性が良い。

### ② プロセスを1つに畳む（差: 200〜400MB）

Dawarich は Rails + Sidekiq + Redis + Postgres の4プロセス。
Web とバックグラウンドジョブを1プロセスに畳めれば数百 MB 浮く。

**これが言語選択と絡む唯一の重要なポイント。** §3 参照。

### ③ スキャンをストリーミングにする（差: 実装次第）

5万枚を一度にメモリへ載せれば**どの言語でも死ぬ**。
Dawarich の Sidekiq OOM はこの類の問題。

**これは言語ではなく実装の問題。** ディレクトリスキャン・EXIF 抽出・サムネイル生成は
すべてストリーミング（1件ずつ処理して即座に解放）で書く。

### 画像処理は言語非依存

**最も重い処理であるデコードとサムネイル生成は libvips / exiftool というネイティブライブラリが行う。**
どの言語から呼んでも実行時間とメモリはほぼ変わらない。**一番重いところが言語に依存しない。**

## 3. 言語比較

| | ベースライン RSS | 単一バイナリ | 1プロセスで HTTP＋バックグラウンド | 画像処理 | ARM64 |
|---|---|---|---|---|---|
| **Go** | **10〜30MB** | ✅ 静的リンク | ✅ goroutine で自然 | govips / exiftool 呼び出し | ✅ `GOOS/GOARCH` だけ |
| **Rust** | 5〜20MB | ✅ | ✅ | libvips バインディング | ✅（ビルドが長い） |
| **TypeScript / Node** | 40〜80MB | ❌ | ✅ worker_threads | **sharp が優秀**（libvips） | ✅ |
| **Python** | 30〜50MB＋依存 | ❌ | △ 工夫が要る | pyvips / pillow-heif | △ wheel 事情に注意 |
| **JVM (Kotlin/Quarkus)** | 100〜300MB | native-image なら可 | ✅ | 選択肢が少ない | ✅ |
| **Ruby / Rails** | 200MB〜 | ❌ | ❌ Sidekiq が別プロセス前提 | 各種 | ✅ |

### 推奨: Go

1. **Timelinize が Go + SQLite でこのワークロードを実装済み。**
   写真＋位置＋タイムライン統合という、ほぼ同じ問題領域での直接の前例
2. **1プロセスで HTTP とバックグラウンドスキャンが同居できる。**
   goroutine と channel だけで済み、Redis も Celery も不要。②の差がタダで手に入る
3. **単一静的バイナリ。** distroless / scratch でイメージが数十 MB。NAS の容量にも優しい
4. **クロスコンパイルが `GOOS/GOARCH` だけ。** NAS の CPU アーキテクチャに悩まされない

### Python も成立する（条件付き）

**「最も速く書ける言語」はソロ開発では実行効率より重要。** 以下を守れば 150〜250MB に収まる。

- FastAPI + uvicorn を **1ワーカー**で動かす
- **Celery / Redis を使わない。** APScheduler か DB バックドのジョブテーブル＋スレッド
- SQLite を使う（①）
- スキャンはジェネレータでストリーミング（③）

**積極的な理由**: 滞在検出は本質的にクラスタリング問題であり、**試行錯誤が最も多くなる部分**。
ここは numpy が効く。

**注意**: scikit-learn を入れると numpy + scipy で 200MB 超＋ARM wheel の問題が出る。
滞在検出は Li らの逐次スキャン型アルゴリズムなら **100 行程度で sklearn 不要**。
依存を足さずに済ませるべき。

### 避けるもの

| | 理由 |
|---|---|
| **Rails** | Dawarich が最低 2GB を要求している実例がある |
| **JVM** | native-image のチューニングが必要になり、本質でないところで時間を使う |
| **Rust** | MVP では開発速度のコストが見合わない。**滞在検出の閾値など未確定な部分が多い段階では特に**。性能が問題になってから一部を置き換えれば十分 |

## 4. 言語非依存で決まっていること

言語の最終決定を待たずに確定できる項目。

| 項目 | 決定 | 理由 |
|---|---|---|
| **DB** | **SQLite（R\*Tree 使用）** | §2 ①。Postgres/PostGIS は過剰 |
| **プロセス構成** | **1プロセス**（Web＋バックグラウンド同居） | §2 ②。ブローカーを持たない |
| **ジョブキュー** | **DB バックド**（Redis を使わない） | プロセスを増やさない |
| **画像処理** | **libvips**（＋読めないものだけ exiftool） | §2。PhotoPrism の二段構えに倣う（`docs/photos.md` §6 ④） |
| **配布形態** | **Docker イメージ**（単一コンテナ） | NAS の標準的な導入手段 |
| **対応アーキテクチャ** | **amd64 / arm64 の両方** | NAS は両方ありうる |

### 目標値

| 指標 | 目標 |
|---|---|
| 常時メモリ | **300MB 以下** |
| スキャン中のピークメモリ | **500MB 以下**（枚数に比例して増えないこと） |
| Docker イメージサイズ | 200MB 以下 |
| 追加で必要な常駐プロセス | **0**（DB もブローカーも持たない） |

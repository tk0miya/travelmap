# 写真データの扱い

写真は GPS と並ぶ本サービスの二本柱である。GPS が「どこにいたか」を与えるのに対し、
写真は「何を見たか」を与える。ここの設計を誤ると、旅行記が骨だけになるか、
逆に写真管理サービスを作る羽目になってスコープが破綻する。

---

## 1. 前提: Google Photos は継続同期に使えない

### 現状（2025年3月31日以降）

Google Photos Library API から以下のスコープが**削除された**。

- `photoslibrary.readonly`
- `photoslibrary.sharing`
- `photoslibrary`

残っているのは `photoslibrary.readonly.appcreateddata` のみで、
**自アプリがアップロードしたメディアしか読めない**。

代替として **Picker API** が新設された。ユーザーがピッカー UI で選んだアイテムだけに
アプリがアクセスできる仕組みで、設計思想として「ユーザーが都度選ぶ」ことを前提にしている。

### 本サービスにとっての意味

**Picker API は「API が無い」より厄介である。** 存在はするが用途が合わない。

- 旅行1回あたり数百枚を**毎回手で選ばせる**運用は成立しない
- 「新しい写真が増えたら自動で取り込む」ができない
- 過去分の一括取り込みもできない

**結論: Google Photos を継続同期のソースとして設計に入れない。**
Google Takeout によるワンショット取り込みだけを、過去分の移行経路として扱う
（Takeout は手動操作であり、定期実行はできない）。

参考: [Picker API launch and Library API changes](https://developers.googleblog.com/en/google-photos-picker-api-launch-and-library-api-updates/) /
[Authorization scopes](https://developers.google.com/photos/overview/authorization)

## 2. 既存 OSS はどうしているか

調査の結果、**はっきり2つの流派に分かれる**ことが分かった。

### 参照モデル — 写真を一切持たない

| プロダクト | 実装 |
|---|---|
| **Dawarich** | 公式ドキュメントで明言: **「写真を保存もコピーもしない。自己ホストの写真サービスから API 経由で位置メタデータを読むだけ」**。設定で Immich / PhotoPrism の URL と API キーを登録する（Immich は `asset.read` と `asset.view` スコープが必要）。地図と旅行ビュー上に表示する |
| **GeoPulse** | 同構造。Immich のライブラリをマップタイムラインに重ねる |
| **Reitti** | 同構造。Immich 連携で位置ベースの写真とギャラリー |

**位置情報 OSS 3つが揃って参照モデル**である。

ただし**彼らはサムネイルすら持たない完全参照**であり、これは実際に問題になっている。
Dawarich には「[Immich 連携で写真が表示されない #1071](https://github.com/Freika/dawarich/issues/1071)」
「[写真がまだ地図に出ない #1608](https://github.com/Freika/dawarich/issues/1608)」といった issue が立っている。

**Immich が落ちる / URL が変わる / API キーが切れると、写真が丸ごと消える。**

### コピーモデル — 原本を取り込む

| プロダクト | 実装 |
|---|---|
| **AdventureLog** | 自前の永続ボリューム（`/var/adventurelog/data`）に保存。ユーザーがアップロードする。加えて Immich から**インポート**（＝コピー）もできる |
| **Timelinize** | **取り込んだデータを timeline フォルダに原本ごとコピーする**。理由も明示されている: **「長期的な安定性と完全性を保証するため」**。日付別に整理し、独自形式を使わず、普通にファイルブラウザで開ける。Google Photos の原本と編集版を両方保持して関連づける。完全重複は取り込まない |

### ここにある相関

```
写真の役割                 保持方針          代表例
──────────────────────────────────────────────────────────
GPS が主役、写真は補助     参照（持たない）   Dawarich / GeoPulse / Reitti
写真が主役                 コピー（持つ）     AdventureLog / Timelinize
```

**写真が主役に近いほどコピーする。** これは偶然ではない。
写真が主役なら、外部依存で消えることは許容できないからである。

### 本サービスの立ち位置

本サービスは**旅行記側、つまり写真が主役に近い**。したがって:

- 純粋な参照モデル（Dawarich 型）では**弱すぎる**。Immich が消えたら旅行記が骨だけになる
- 原本を全部コピーするモデル（Timelinize 型）では**スコープが破綻する**。写真管理サービスを作ることになる

**次節の3層分離は、この2流派のちょうど中間を狙うものである。**

Timelinize の「長期安定性のためにコピーする」という主張は正しい。
ただし**サムネイルだけ持てば容量は1/10〜1/50で、長期安定性の大部分が得られる**。
Immich が消えても旅行記は読める。失われるのは拡大表示だけ。

## 3. 中核方針: 写真を3層に分けて持つ

写真を「1つのもの」として扱わない。**保持方針の異なる3つの層**に分解する。

| 層 | 保持方針 | サイズ感 | 失われたときの影響 |
|---|---|---|---|
| **メタデータ** | **必ず自前で持つ** | 数百バイト / 枚 | 旅行記が組めなくなる。**致命的** |
| **サムネイル** | **自前で持つ** | 数百 KB / 枚 | 旅行記が文字だけになる。痛い |
| **原本バイナリ** | **持たない**（参照のみ） | 数 MB / 枚 | 拡大表示ができなくなるだけ。**旅行記は壊れない** |

### なぜこう分けるのか

**原本へのリンクが切れても旅行記が壊れないようにするため。**

写真の原本は重く、所有権が曖昧である。Immich にあるかもしれないし、NAS にあるかもしれないし、
iPhone にしかないかもしれない。写真管理サーバを乗り換えることも、NAS を入れ替えることもある。

そのたびに旅行記が壊れるのは許容できない。一方、メタとサムネは軽いので自前で抱えられる。
**この2つさえ手元にあれば、旅行記は何年でも生き残る。**

逆に原本を自前で抱え込むと、ストレージ管理・バックアップ・重複排除・トランスコードと
写真管理サービスの仕事が全部降ってくる。これは `docs/concept.md` の非目標に反する。

## 4. 取り込み経路

### 選択肢は「外部 API 連携」対「ローカル読み取り」の2択ではない

この2つの間に、重要な選択肢が隠れている。**軸は「原本の所在」と「自前で持つもの」の2つ**であり、
組み合わせると4案になる。

| | 原本の所在 | 自前で持つもの | 前例 |
|---|---|---|---|
| **A. 完全オーケストレーター** | 外部サービス | 何も持たない | Dawarich / GeoPulse / Reitti |
| **B. インデクサ型** | **ローカル / NAS のまま** | メタ＋サムネ | **Immich の external library**、PhotoPrism の read-only mount |
| **C. 取り込み型** | 自前にコピー | 全部 | Timelinize |
| **D. アップロード型** | 自前にコピー | 全部 | AdventureLog |

**B（インデクサ型）が要点である。** 「ローカルファイルを読む」と「原本を持たない」を両立させる。
フォルダをマウントしてスキャンし、メタデータとサムネイルだけ自前 DB に持つ。
**原本はその場にあるまま、1バイトもコピーしない。**

**Immich 自身が external library としてこの方式を持っている**ことは重要な傍証である。
写真管理のデファクトが「コピーしないモード」を用意しているのは、この需要が実在するということ。

### セットアップしやすさは直感と逆になる

「外部サービス連携のほうが第三者に優しい」は**誤りである**。

| 方式 | 第三者のセットアップ手順 |
|---|---|
| A. オーケストレーター | **「まず Immich を立ててください」** → Docker Compose、DB、機械学習コンテナ、モバイルアプリ設定 |
| B. インデクサ型 | **「写真フォルダをマウントしてください」** → `volumes:` を1行 |

**A は前提条件に別プロダクトの構築が丸ごと入る。** これは事実上の脱落要因になる。

B は写真の入ったフォルダさえあれば動く。NAS でも、PC のピクチャフォルダでも、外付け HDD でもよい。
**Google Photos の Takeout を展開したフォルダも同じ経路で処理できる**ため、
取り込み経路を増やさずに Google Photos 利用者を拾える。

### 決定: B を MVP、A を第2段階、C / D はやらない

**B を MVP にする理由**

1. **外部依存ゼロで動く。** 写真フォルダがあれば誰でも試せる
2. **Takeout も同じ経路で処理できる。** Google Photos 利用者を経路追加なしで拾える
3. **NAS 運用と噛み合う。** 「Google Photos と NAS の両方に転送」という一般的な運用では、
   NAS 側が原本の正本になっており、Google Photos は閲覧用の複製にすぎない。
   NAS を読めば必要なものは全部揃う

**A を第2段階に入れる理由**: **B には iPhone の写真を自動で流し込む経路が無い。**

iOS の PhotoKit はアプリ内からしか使えず、サーバから叩けない。
「iPhone の写真を自動でサーバに集める」には自前のモバイルアプリが要り、MVP のスコープを大きく超える。

一方 **Immich は iOS / Android の自動バックアップアプリを持っている**。
そこに乗れば、写真がサーバに集まるところまでは Immich が面倒を見てくれる。
本サービスは Immich の API からメタデータとサムネイル URL を取るだけでよい。

既存の位置情報 OSS（Dawarich / GeoPulse / Reitti）が揃って Immich 連携を実装しているのは、
同じ事情によるものと考えられる。

**C / D をやらない理由**: 原本を自前で抱えると、ストレージ管理・バックアップ・
重複排除・トランスコードという写真管理サービスの仕事が全部降ってくる（D-08）。

### 汎用化コストはどこにかかるか

「取り込み経路を増やすと汎用化コストがかかる」という懸念は、**コストの発生場所を取り違えている**。

コストが高いのは経路の数ではなく、**内部表現がソースごとに違うこと**である。

```
❌ 経路ごとに内部表現が違う
   ローカル読み取り → PhotoRecord 型 → 表示ロジック A
   Immich 連携     → ImmichAsset 型 → 表示ロジック B
   → 機能追加のたびに両方直す。永続的なコスト

✅ アダプタ層で正規化
   ローカル読み取り ─┐
   Immich 連携     ─┼→ Asset（統一） → 表示ロジック（1つ）
   Takeout 展開    ─┘
   → 経路追加は各 50〜150 行程度。1回きりのコスト
```

**アダプタ層を最初に作るコストは1回。作らないコストは永続。**
D-02 で決定済みのアダプタ層が、そのままここに効く。

### 各経路の実装メモ

**B: インデクサ型（MVP）**
- 設定でスキャン対象のディレクトリを指定（Docker なら volume マウント）
- 再帰的にスキャンし、EXIF を抽出して Observation 化、サムネイルを生成
- `original_ref` にファイルパスとコンテンツハッシュを保存。**原本はコピーしない**
- 差分スキャン（mtime とパスで既知ファイルをスキップ）
- **ファイルが移動・削除されても、メタとサムネは残る。** 旅行記は壊れない
- Google Takeout の展開ディレクトリもこの経路で処理する

**A: Immich 連携（第2段階）**
- Immich の API からアセット一覧とメタデータを取得
- サムネイルは取得して**自前でキャッシュする**（参照だけにしない。D-08）
- `original_ref` に Immich の asset ID を保存
- ローカル読み取りと同じ写真が両方から入りうるため、重複排除が必須（§5 ⑥）
- **注意**: Immich の external library を read-only でマウントしている環境では、
  Immich 側が XMP サイドカーを作れずメタデータ編集ができない。
  本サービスは**読むだけ**なので影響しないが、ユーザーの環境把握として文書化する

## 5. 実装上の落とし穴

設計に跳ね返る問題。**すべて実装前に手当てが必要。**

### ① EXIF の撮影時刻にタイムゾーンが無い（最重要）

`DateTimeOriginal` は「2026-03-14 14:20」としか記録しない。**どこの 14:20 かが分からない。**

EXIF 2.31 (2016) で `OffsetTimeOriginal` / `OffsetTime` / `OffsetTimeDigitized` が追加されたが、
**書く機種と書かない機種がある**。iPhone は書く。多くのデジカメは書かない。

これは決定事項 **D-07（全観測を UTC 保存）と正面衝突する**。

**解決策（優先順に試す）**

1. `OffsetTimeOriginal` があればそれを使う
2. 写真に GPS 座標があれば、座標から IANA タイムゾーンを導出する
3. 座標が無ければ、**時間的に最も近い GPS 観測の TZ を借りる**
4. それもできなければ「TZ 不明」として保持し、Trip に紐づいた後に Trip の `home_tz` で解決する

3 の仕組みは `docs/features.md` の F-02 に既に設計済みであり、そのまま流用できる。

**「TZ 不明」を NULL で誤魔化さない。** 不明であることを明示的に持ち、後から解決できるようにする。

### ② 位置情報の無い写真が大量にある

以下はすべて位置情報を持たない。

- 位置情報記録をオフにしている
- スクリーンショット
- 他人から受け取った画像（LINE、AirDrop）
- スキャンした紙焼き写真

**対処: 時刻だけで GPS 軌跡に突き合わせ、位置を逆算する。**
「この時刻にはここにいた」が分かっていれば、写真の位置も分かる。

ただしこれは**推定**なので、EXIF 由来と明確に区別する。

```
location_source: exif | inferred_from_gps | user_set | unknown
```

UI 上でも「この写真の位置は推定です」と示せるようにする。
`docs/data-model.md` の `place_source` / `mode_source` と同じ思想。

### ③ 公開ページでの EXIF 漏洩（セキュリティ）

**公開する旅行記に原本サイズの写真を出すと、EXIF 経由で情報が漏れる。**

EXIF に含まれうるもの:

- 自宅で撮った写真の GPS 座標
- カメラのシリアル番号（個体の追跡が可能になる）
- 撮影者名・著作権表記に入れた本名
- 元のファイルパス（ユーザー名が含まれることがある）

`docs/decisions.md` D-03 で「公開ページに旅行と無関係な位置情報を含めない」と書いたが、
EXIF 経由の漏洩を明示していなかった。

**対処: 公開用の画像は必ず再生成し、メタデータを全て落とす。**
原本をそのまま配信しない。これは例外を作らない。

### ④ HEIC は JPEG と同じ経路では読めない

HEIC の EXIF は ISO BMFF のボックス内にあり、JPEG 用のパーサでは読めない。

**選択肢**

| 方式 | 利点 | 欠点 |
|---|---|---|
| exiftool を外部プロセスで呼ぶ | フォーマットカバレッジが圧倒的、事実上の標準 | プロセス起動コスト、外部バイナリ依存 |
| ネイティブライブラリ | 速い、依存が少ない | 対応フォーマットが限られる、エッジケースに弱い |

**PhotoPrism は両方を使う二段構え**（ネイティブパーサ + exiftool オーバーレイ）を採用している。
大量取り込み時はネイティブで速く処理し、読めないものだけ exiftool に回す設計であり、
これは真似する価値がある。

加えて、**ブラウザは HEIC を表示できない**。サムネイル生成時に JPEG / WebP へ変換する必要がある。

### ⑤ Live Photos とバースト撮影

- **Live Photo** — 1枚の写真が HEIC + MOV の2ファイル。別々に取り込むと二重に見える
- **バースト** — 同じ瞬間に10枚。タイムラインが埋まる
- **HDR / 編集版** — 元画像と編集後が両方存在することがある

**対処: 撮影時刻の近さ＋位置の近さでグルーピングし、代表1枚を表示する。**
グループは展開して全部見られるようにする。

### ⑥ 重複

同じ写真を複数経路から取り込むことがある（Takeout からも Immich からも入ってくる）。

**単純なバイト一致では排除できない。** Google Photos は再エンコードするため、
Takeout 経由の写真は原本とバイト一致しない。

**対処: 「撮影時刻 + カメラ機種 + 元画素数」の組み合わせを重複判定キーにする。**
必要なら知覚ハッシュ（pHash）を併用する。完全自動で消すのではなく、
**候補を提示して人が確定する**（`docs/data-model.md` の Place 名寄せと同じ方針）。

### ⑦ 向き（Orientation）

EXIF `Orientation` を無視すると写真が横倒しになる。
**サムネイル生成時に回転を焼き込む**こと。原本を書き換えてはならない。

## 6. データモデルへの反映

写真は Observation（`source = photo_exif`）として取り込むが、
**サムネイルと原本参照を持つため、専用の Asset を別に持つ**。

### Asset（写真アセット）

| フィールド | 型 | 説明 |
|---|---|---|
| `id` | ID | |
| `observation_id` | ID | 対応する Observation |
| `kind` | enum | `photo` / `video` / `live_photo` |
| `group_id` | ID, nullable | Live Photo / バーストのグループ |
| `is_group_primary` | bool | グループの代表か |
| `captured_at` | timestamp | UTC。TZ 解決後の値 |
| `captured_tz` | string, nullable | 解決した TZ |
| `tz_source` | enum | `exif_offset` / `from_coords` / `borrowed_from_gps` / `from_trip` / `unknown` |
| `lat` / `lon` | float, nullable | |
| `location_source` | enum | `exif` / `inferred_from_gps` / `user_set` / `unknown` |
| `orientation` | int | EXIF Orientation |
| `thumbnail_path` | string | **自前で保持するサムネイル** |
| `original_ref` | JSON | 原本への参照。`{"kind":"immich","asset_id":"..."}` / `{"kind":"file","path":"...","hash":"..."}` |
| `dedup_key` | string | 重複判定キー（撮影時刻＋機種＋画素数） |
| `camera_make` / `camera_model` | string, nullable | |

**`original_ref` が解決できなくなっても、`thumbnail_path` と メタデータで旅行記は成立する。**
これが3層分離の実利である。

## 7. 機能への反映

`docs/features.md` に以下を反映する。

**MVP**
- F-01 に HEIC の二段構えパース、Orientation 焼き込み、グルーピング、重複排除を明記
- F-02 に写真の TZ 解決の優先順位（上記①の4段階）を明記
- 写真の位置逆算（②）を F-04 の重ね合わせに含める

**第2段階**
- Immich 連携（B 経路）
- F-14（公開ページ）に **EXIF 全除去** を受け入れ条件として追加

**対象外**
- Google Photos の継続同期（不可能）
- 原本バイナリの自前保管
